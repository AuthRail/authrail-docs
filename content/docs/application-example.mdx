This recording shows an assistant using business tools with AuthRail. It can
read information, ask to make changes and return useful results, while the
organisation's Rails determine which requests may proceed and which information
may reach the assistant.

The example runs locally, with Stripe in test mode and application release
records stored in a local sample ledger. The release tools do not deploy to a
cloud service. It illustrates how AuthRail fits into an application rather than
providing a hosted application for you to connect to.

## Understanding the decisions

The Stripe requests illustrate why a rule needs the right business information.
A payout is limited by the funds currently available in the requested currency,
whereas a refund is limited by the remaining refundable amount on its payment.
Those values come from the provider through the application, so the rule can
follow the state of the account or payment rather than relying on a fixed
amount entered into a prompt.

When a request is denied, AuthRail stops the connected function before it sends
the write to the provider. An allowed request can still encounter a provider
error, however, and the application's completion report remains separate from
the permission decision. The Action in AuthRail lets you follow the request and
its reports; the matching Stripe record is where you check the provider effect.

The settings and API-key examples show the other side of the boundary: checking
what comes back from a tool. The assistant can receive useful settings with a
credential field removed, while a request for raw keys has its result withheld.
The credentials in this example are inert sample values. Checking a result
controls what is returned to the assistant; it cannot undo an operation that
has already run.

## When a rule needs interpretation or human review

The release example uses AuthRail Contextual AI to assess the application's
release notes. The Rail defines what the assessment should look for and which
material may be sent to AuthRail. Its finding is then used by the local rule
engine to decide how the request should be handled. An uncertain assessment
cannot satisfy a rule that needs a clear answer.

Some requests need a person's judgement instead. In that case the application
saves the request while the named reviewer considers it in AuthRail. Once the
review is complete, the application can continue the saved work using the
approved input and current permission. This requires a continuation in the
application; clicking Approve does not execute the business operation by itself.
The [approvals guide](/docs/approvals) explains that workflow in detail.

## Bringing this into your application

The assistant's model interprets the person's words and proposes a tool request.
Your application identifies the caller, selects the account or resource, and
passes the operation through the SDK and sidecar before performing the work.
That separation lets people ask for the same task in different ways while the
authorization check remains tied to the operation and its business values.

[Building your own app](/docs/build-your-app) explains where to put those checks.
To try the integration, follow the [quickstart](/docs/getting-started) with a
local invoice reader, then use the [Rails guide](/docs/rails) to develop your
rules. The [compatibility reference](/docs/compatibility) identifies the published
SDK and sidecar capabilities, since the application in this recording uses
source features that are not all included in the older released packages.
