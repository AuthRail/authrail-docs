A **human approval** gives a named person a chance to decide before an action
proceeds. Your organisation might let an agent read invoices automatically,
for example, while asking someone to review a proposed payment. In Enforce,
the application saves that payment request and waits for the required decision.

Approval gives permission to continue the request you reviewed. The originating
application still has to resume it and perform the work, so the approval and
its eventual execution appear separately on the Action.

## Review and continue a request

1. In <a href={AUTHRAIL.clientOrigin}>AuthRail</a>, open **Actions & decisions → Approvals for you** with the account named in
   the approval setup. You can also review through the Action detail when its
   controls are available to you. If a request is missing, ask its owner to
   check the named reviewer list.
2. Read the requested action, reason, values and **Expires** time. For a payment,
   consider the amount, account and purpose shown on this request. These are the
   values the application saved for review, rather than a replacement discussed
   later in chat.
3. Choose **Approve** or **Reject**, or **Cancel request** when your authority
   allows it. If the setup needs several approvals, your vote contributes to
   that number, called the **quorum**.
4. After approval, return to the application that made the request. The reference
   chat uses **Check approval**, followed by **Continue saved request** when
   approval is confirmed. Other applications provide their own continuation
   control.

After continuing, open the linked Action to see what the application reported
and whether its result passed the release check. A rejected, cancelled or
expired request stays in history without giving permission to run through that
approval. An unclear outcome after resumption needs [recovery](/docs/recovery).

## Understand the approval deadline

The **Expires** time follows the configuration and facts used by the request.
For example, a balance read at 10:00 with a five-minute freshness limit cannot
support an approval after 10:05. Another request without that short-lived
reading may have a longer window. The deadline never outlasts the signed
deployment configuration used for its decision.

Read the displayed time rather than assuming a fixed review period. There is
no separate arbitrary 48-hour setting, and renewing configuration or selecting
a newer Rail does not extend an existing approval. Once it expires, the
application needs a fresh decision. The Rail itself can remain published.

## Save and resume the application's work

Your application can wait for review without keeping an HTTP request or agent
process open. When the SDK reports that approval is required, it supplies an
**approval continuation**: the original call and decision needed to resume.
Save this with the application's task so a later worker or user action can
continue the same work after approval.

The application should store the continuation privately and persist any user,
conversation or workflow state it will need afterward. The continuation contains
the checked call, not a backup of the whole agent session. When resuming, one
worker claims the task, loads that saved data, and passes it to the SDK with
the original business function. The SDK then claims a one-use permit, records
the start, runs the function and checks its result.

### Save the checked call, then resume it

These examples continue the [SDK setup](/docs/getting-started) with an Enforce
client. `operation` contains the action description, authenticated identities,
stable business request key and review summary; `payment` is the application's
validated input. `payInvoice` or `pay_invoice` is the function that performs it.

The `tasks` store is application code. Its helpers must encrypt the continuation
and bind it to the original organisation, authenticated user, deployment and
task ID in `binding`. A resume worker claims that task exclusively before
loading it. Load the saved call from this store, rather than accepting a
continuation or new arguments from the browser or agent.

The submit handler returns “Awaiting approval” after saving. The resume function
runs in a later invocation, once the required review is complete.

<Tab value="Node.js">

```ts
import { EnforceBlockedError } from '@authrail/sdk-node';

async function submitPayment() {
  try {
    await client.enforce(operation, payment, payInvoice);
  } catch (error) {
    if (!(error instanceof EnforceBlockedError) ||
        error.phase !== 'tool_call' || error.effectMayHaveOccurred ||
        !error.approvalContinuation) throw error;
    await tasks.saveEncrypted(binding, JSON.stringify(error.approvalContinuation));
    // Return "Awaiting approval" to the caller; do not hold the HTTP request open.
  }

}

async function resumePayment() {
  // Claim the saved task exclusively before calling this function.
  const saved = await tasks.loadEncrypted(binding);
  await client.resumeApprovalFrom(JSON.parse(saved), payInvoice);
}
```

```go
// Imports: context, encoding/json, errors, and authrail "github.com/AuthRail/authrail-sdk-go".

func submitPayment(ctx context.Context) error {
    _, _, _, err := authrail.Enforce(ctx, client, operation, payment, payInvoice)
    if err == nil { return nil }
    var pending *authrail.ApprovalRequired
    if !errors.As(err, &pending) { return err }
    continuation, err := pending.Continuation()
    if err != nil { return err }
    encoded, err := json.Marshal(continuation)
    if err != nil { return err }
    // The store records this task as awaiting approval.
    return tasks.SaveEncrypted(ctx, binding, encoded)
}

func resumePayment(ctx context.Context) error {
    encoded, err := tasks.LoadEncrypted(ctx, binding)
    if err != nil { return err }
    var continuation authrail.ApprovalContinuation
    if err := json.Unmarshal(encoded, &continuation); err != nil { return err }
    _, _, err = authrail.ResumeApprovalFrom(ctx, client, continuation, payInvoice)
    return err
}
```

from authrail import ApprovalContinuation, EnforceBlockedError

async def submit_payment():
    try:
        await client.enforce(operation, payment, pay_invoice)
    except EnforceBlockedError as blocked:
        if (blocked.phase != "tool_call" or blocked.effect_may_have_occurred
                or blocked.approval_continuation is None):
            raise
        await tasks.save_encrypted(
            binding, json.dumps(blocked.approval_continuation.as_dict())

async def resume_payment():

    continuation = ApprovalContinuation.from_dict(json.loads(saved))

The SDK checks the saved request before claiming permission. A request still
waiting, rejected, expired or already consumed cannot resume through the same
approval. Keep a failed resume available for inspection rather than marking
its task completed or starting another payment. If the tool may have run,
follow [execution recovery](/docs/recovery).

A changed amount, account or target is a new request that needs its own decision.
That lets a person explicitly request different work after a denial without
turning it into an automatic retry. Splitting requests to evade a rule, or
changing keys to conceal an uncertain original effect, does not resolve the
original request.

## Let reviewers know they have work

AuthRail creates an in-app notice for active named reviewers when a request is
ready. In notification settings, reviewers can enable Runtime email with a
verified address. Email is opt-in and leaves the request values on the signed-in
review screen, so the notice can direct someone to the right organisation and
approval without sending those details through email. A queued message describes
delivery work still pending, not confirmation that the recipient received it.

<details className="guide-details">
<summary>Choose reviewers and provide useful review context</summary>

A Runtime manager opens a Rail for the action and its **Approval reviewers**
section. Under **Who can approve this action?**, choose active organisation
members and the number required, then **Save reviewers**. This needs Rail
publishing and AI Inventory management access. The selection belongs to that
action version and is shared by its Rails.

A named authorised reviewer may also be the requester where permitted. Their
explicit decision is still recorded, although it does not represent independent
review by another person. Choose and operate the reviewer policy accordingly
when separation of duties is needed.

The developer supplies a signed `reviewSummary` with a short title and enough
business information to decide. A valid summary is required to enter approval;
it should explain the request without including credentials, raw prompts or
complete provider responses.

</details>

<details className="guide-details">
<summary>Approval expiry and the shorter execution permit</summary>

A signed deployment configuration lasts 24 hours from activation or renewal.
Approval uses what remains of that period, shortened further by the facts it
relies on. Renewing the deployment does not refresh that earlier request.

After approval, the SDK claims a one-use execution permit lasting up to 30
seconds, or less if the request or signed proof expires sooner. The application
must establish its start report within that period. This is the window to
begin the attempt, not a 30-second review deadline or a requirement that the
business function finish within 30 seconds.

</details>

<details className="guide-details">
<summary>Resume APIs and a lost permit response</summary>

| SDK | Same-process continuation | Saved continuation | Lost permit response |
| --- | --- | --- | --- |
| Node | `resumeApproval` | `resumeApprovalFrom` | `recoverApprovalFrom` |
| Go | `ResumeApproval` | `ResumeApprovalFrom` | `RecoverApprovalFrom` |
| Python | `resume_approval` | `resume_approval_from` | `recover_approval_from` |

The application supplies persistence and restores the original function and
arguments. If a permit response was lost, recovery can read an existing valid
permit for an attempt that has not started. It does not create another permit
or authorise an already started attempt. Keep execution stopped if permission
cannot be established, and inspect the Action; investigate the effect instead
if the function may already have run.

A result check may encounter the same approval condition because it also sees
the business arguments. The SDK can release that result using the original
Action's claimed permit. A denied, absent or mismatched result remains withheld,
even when the operation itself completed.

</details>
