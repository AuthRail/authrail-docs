The SDK in your application and the sidecar beside it work together to check
tool calls. When choosing or upgrading them, you need to answer two questions:
can these versions work together, and do the application’s tools go through
their checks?

The first question is **compatibility**. The components must understand the
same requests, decisions and recovery information. The second is **coverage**:
an invoice reader is protected only if calls to it pass through the SDK wrapper.
Installing compatible components will not protect another route that calls the
provider directly.

Use this page to choose your versions and plan a check of the application after
installation or an upgrade.

## Choose the SDK for your application

| Your application | Start here |
| --- | --- |
| JavaScript or TypeScript tool functions | [Node SDK](/docs/node). |
| Go functions or HTTP handlers | [Go SDK](/docs/go). |
| Async Python functions and scripts | [Python SDK](/docs/python), using Python 3.11 or newer. |
| An agent running inside NVIDIA OpenShell | [OpenShell integration](/docs/openshell), with the protected application and SDK outside the sandbox. |

Run the sidecar with [Docker](/docs/docker), the recommended setup, or use a
[native binary](/docs/native). Both run the same local decision process.

## Install the SDK and sidecar

Install the SDK for your application's language and download sidecar version
**{AUTHRAIL.releases.sidecarVersion}**. The sidecar download contains one program,
`authrail-sidecar`. You can ask that program to start a Docker container, or run
the sidecar directly on your computer with `--runtime native`. “Native” means
running the program directly, without Docker.

## Released capability boundary

SDK 0.1.1 supports Observe and Enforce wrappers, application signing, saved
approval continuations and reconciliation of uncertain operations. It also
includes interfaces for application-supplied Guard handlers and explicit fact
readers. Start with a Policy Rail that compares ordinary input fields, as in
the invoice quickstart.

Automatic Rail-owned Contextual AI, the expanded built-in Guard protections and
automatic Data reader bindings need newer integrations than SDK 0.1.1 provides.
Before enabling those requirements, choose a released SDK and Runtime that
support them together. The Rail editor and current repository source can
describe capabilities that an older installation cannot fulfil. Missing
handlers or readers must leave the check unavailable rather than letting a
required rule pass.

The older provider-specific extractor interface is not the setup for AuthRail
Contextual AI. That feature is operated by AuthRail and does not ask customers
for model credentials. The [Contextual AI guide](/docs/facts) explains its
material disclosure and assessment flow.

The recording illustrates the versions used in that application. Use the table
above for package installation, then test your own protected function. If you
also use OpenShell, record its version and policy; that guide covers the 0.1.6
integration.

## Check the protected operation

In a safe application or provider test account:

1. **Try an allowed request in Enforce.** Inspect its call and result checks,
   execution start and reported completion.
2. **Try a denied request.** Check the effect record or provider account to
   establish that the operation did not run.
3. **Try a request needing approval.** Review it, then continue the saved
   request through the application's approval flow.
4. **Check reporting failure and recovery.** Confirm that permission saved only
   in a local queue cannot start Enforce execution. Use the
   [recovery guide](/docs/recovery) to test a lost response without duplicating
   a business effect.
5. **Review other routes to the same action.** Follow the
   [security guide](/docs/security), including credentials, tools and network
   paths that could bypass the protected application.

After these checks, your deployment notes should identify the versions tested,
the operations that pass through protection and any routes or failure cases
still needing attention. Compare the provider’s record with the application’s
report when checking an external effect; permission alone does not establish
that the provider completed it.

<details className="guide-details">
<summary>More about protocol versions and upgrades</summary>

The signed bundle and local evaluation use `formatVersion: 1`. This names a
message format. It does not by itself establish compatible recovery behavior
or coverage of every tool.

For implementation details, the sidecar archive includes `COMPATIBILITY.md`
and shared examples under `conformance/v1`. These describe message formats and
help maintainers check consistent signing and decision handling. They complement
your application checks: upgrading one component can still change the way an
integration behaves. Use the supported SDK for signing and recovery, and verify
the versions you intend to run together.

Before replacing a running instance, preserve the entire sidecar state set,
application recovery records, keys and pending approvals. Verify the new
combination in a safe installation first. Review coverage again when changing
sandbox access, provider accounts, processing handlers or network permissions.
A missing handler or unavailable required isolation cannot be treated as a
passing Enforce check.

</details>

## Release identities for upgrades and support

<details className="guide-details">
<summary>Versions, Docker images and build identities</summary>

The downloaded sidecar program and the Docker image it starts are separate
release artifacts. Version 0.2.0 of the program selects an older Docker image;
it does not automatically select the Docker tag with the same version number.
These details help you identify an existing installation or discuss an upgrade.
The installation guides show which command to run without asking you to choose
an image manually.

| Installed component | Identity |
| --- | --- |
| Sidecar program 0.2.0, also used when running without Docker | Revision `1f436c89d52f6e19c778fda561815cb7c27415ea`. |
| Docker image started by that program | Reported version `0.1.0`, revision `5547cc5041558aaa23437b484e7a789600de6c5e`, image digest `sha256:cb6e60475146ead55bcec56d5da14fcc75e2bf7e776b584b01ace5426a5356f4`. |
| Docker tag `0.2.0`, published separately | Image digest `sha256:5ca550de03a591c42d490374229bca57980b3e000b7b86bb3366174b317b48b4`; Linux amd64 and arm64. Guided setup does not choose this image. |

An image digest identifies the contents of a container image. A tag is a name
that can later point to different contents. Keep the installed SDK version,
program version and Docker image digest in your deployment notes. Preserve the
installation's private connection files and state before an upgrade, and check
the required capabilities as well as the version numbers.

</details>
