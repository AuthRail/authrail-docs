AuthRail Runtime connects your organisation's rules to the functions an AI
application uses to do work. It checks a request before a connected function
runs and can check its result before information returns to the agent. This
allows you to control an operation at the point where it happens, while your
application continues to own its business logic and provider connections.

For example, a finance assistant might be allowed to read invoices but need a
person's approval before creating an estimate. Runtime gives the application a
way to apply those rules consistently and keep the request, decision, approval
and execution reports together for later review.

## What happens when the agent asks to use a tool?

The assistant's model interprets the person's message and proposes a tool call,
such as reading an invoice. Your application then identifies the caller and
checks which invoice they are permitted to access. It sends the operation and
that information through an AuthRail SDK to the sidecar running beside it.

The sidecar evaluates the request using the deployment's published Rails. In
Enforce mode, the SDK lets the function continue only when it has the required
permission and recording confirmation. A denied call stops before the function
runs, while a request needing approval is saved for its reviewer. When an
allowed function returns, the SDK checks the result before releasing it to
the assistant and reports what happened during the attempt.

This is why the flexibility of a chat interface and the authorization decision
are separate. The model can turn several differently worded messages into the
same tool request; the deterministic engine checks the resulting operation and
its values against the rules. Ordinary conversation does not automatically
create an Action or pass through every kind of Rail. The [app-builder
guide](/docs/build-your-app) explains how to connect these responsibilities in
your own application.

## The application, SDK and sidecar

An **SDK** is the library you add to your Node.js, Go or Python application. It
connects the language's function calls to Runtime, submits the checks and
reports, and applies the decision around the business function. Your application
supplies the authenticated caller, the permitted resource and the credentials
needed to carry out the operation.

The **sidecar** is a separate process you run beside that application. It loads
the deployment's signed rules from AuthRail, evaluates requests locally and
sends decision and execution reports back to the workspace. Keeping evaluation
in one sidecar implementation allows the language SDKs to use the same rule
engine. It also gives your operator a separate process to monitor, with its own
persistent state and report-delivery queue.

In the <a href={AUTHRAIL.clientOrigin}>AuthRail workspace</a>, your team reviews the AI system, prepares and
publishes Rails, selects the versions for each deployment, handles approvals
and inspects its records. [Management MCP](/docs/mcp) provides assistant tools for
supported work in that workspace, using the connected person's permissions.
The application's SDK integration is still what checks the business function;
management access alone does not connect its other tools.

The [quickstart](/docs/getting-started) walks through these parts with a local
invoice reader. Use the [Docker](/docs/docker) or [native](/docs/native) guide for
the sidecar, according to where your application runs.

## How Rails contribute to a decision

A **Rail** expresses a rule your organisation wants to apply to an action.
Different kinds of Rail contribute different parts of the check. A Guard can
restrict the input or information returned by a tool, a Data Rail can supply a
trusted business value, and a Policy Rail can apply the organisation's business
authority using those values.

For a payout, the application might obtain the account's available funds in the
requested currency and let a Policy Rail compare that value with the requested
amount. For a release, a Rail might use AuthRail Contextual AI to assess whether
selected release notes describe weakened authentication. In that case the
permitted material is sent to AuthRail for interpretation, and its finding is
used by the local deterministic engine. Required local filtering happens before
that disclosure, and an uncertain finding cannot satisfy a required check.

The [Rails guide](/docs/rails) explains authoring and publication, while
[Data and Contextual AI](/docs/facts) explains how a rule obtains the information
it needs. Check [compatibility](/docs/compatibility) when choosing these features:
the current editor supports capabilities that are not all included in the
older published SDKs.

## Observe first, then enforce the connected path

A deployment runs in either **Observe** or **Enforce**. Observe helps you see
what your rules would decide while the application continues under its normal
behaviour. It is useful when introducing an integration or trying rules against
safe requests, because you can inspect the decisions before making them a
condition of execution.

Enforce changes that relationship: the connected function must obtain permission
before it runs, and its result must pass the release check before the agent
receives it. Before relying on this protection, review other routes to the same
operation. If the agent can use an unwrapped tool or read the provider credential
directly, that route remains outside the check. [Observe and Enforce](/docs/modes)
explains the transition, and [execution security](/docs/security) explains what
to review around the application.

## Reading the decision and outcome

An **Action** brings the checks, any approval and the application's execution
reports together. It helps you understand which rules applied and why a request
was allowed, stopped or held for review.

An allowed decision establishes permission for the checked request. Completion
reported means the application said it completed the operation; a provider's
own record can establish the external effect. These may differ when the provider
rejects a request or the application loses a response. A result can also be
withheld after an operation has already happened. [Actions and records](/docs/records)
and [recovery](/docs/recovery) explain how to investigate these situations without
repeating an uncertain write.

<details className="guide-details">
<summary>How the sidecar receives and preserves rules</summary>

A deployment identifies one installation of an AI system and its selected Rail
Versions. Publishing a Rail creates a new version for review and selection;
it does not automatically replace the version every deployment uses. The
sidecar checks for configuration updates every five seconds by default and
verifies the signature, deployment identity, validity and sequence of an update
before replacing the accepted configuration.

The sidecar keeps that configuration in memory and in its local state file,
which it verifies again after a restart. Docker installations preserve the
whole state directory in a volume so rules and queued reports survive container
replacement. A signed configuration has a validity deadline, so cached rules
cannot authorize new Enforce operations indefinitely after expiry. Follow
[monitoring](/docs/operations) and [recovery](/docs/recovery) when a connection
or configuration needs attention.

An AI Inventory item identifies the system your organisation reviews. Its
configuration can describe the provider and model in use, but does not prove
which model generated a particular request. Each connected function also uses
a reviewed **Operation Version**, describing its inputs, results and identity
requirements. [Identity and deployment](/docs/identity) explains these bindings.

</details>

## Connecting Runtime to governance

Runtime records can help a team demonstrate how a process operated, but the
question being assessed still matters. A Control's Test or Evidence requirement
must define which requests, period, coverage and review qualify as proof.
[Using Runtime records in a Control](/docs/framework-proof) shows how to connect
those records to the wider Policies, Controls and Framework workflow.
