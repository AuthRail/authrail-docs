import { AUTHRAIL } from '@/lib/constants';

The sidecar runs beside your application and checks requests against the Rails
you selected in AuthRail. If your invoice reader runs in a container, it can
share a private local connection with a sidecar container. The agent stays
outside that connection, while your application keeps the credentials needed
to perform the work.

This guide uses the released setup executable to start the container for you.
You need Docker Engine or Docker Desktop, a macOS or Linux terminal, and the
[downloaded executable](/docs/native#1-download-the-sidecar). You do not need Go,
a source checkout or a local image build.

First prepare the action, published Rail and deployment in
<a href={AUTHRAIL.clientOrigin}>your AuthRail workspace</a>, following the
[quickstart](/docs/getting-started). The command below connects to
<a href={AUTHRAIL.apiOrigin}>{AUTHRAIL.apiOrigin}</a>.

## 1. Connect this deployment

From the directory containing the downloaded executable, run:

<CommandBlock lang="bash" code={`./authrail-sidecar setup --api-url ${AUTHRAIL.apiOrigin} \\
  --directory "$HOME/.local/share/authrail/my-deployment" --runtime docker`} />

Sign in when the browser opens and select the organisation and deployment.
Setup creates a signing key for the application and registers its public key
with AuthRail. It saves the credentials and SDK helper files privately, then
downloads a prebuilt image and starts the sidecar container. Separate Docker
volumes hold the sidecar’s state and credentials across restarts; the
application’s private signing key stays outside the sidecar.

Wait for **Sidecar has a valid signed rule bundle**. A rule bundle is the
configuration AuthRail sends for this deployment, signed so the sidecar can
verify its origin. Setup also prints the container name and the network setting
your application will need. You will connect the application in step 3.

The setup program downloads the Docker image automatically. The published
versions support the first Policy Rail example; check the
[compatibility guide](/docs/compatibility#released-capability-boundary) before
adding automatic Data readers, expanded Guards or Contextual AI.

## 2. Check the installation

```sh
./authrail-sidecar installation status \
  --directory "$HOME/.local/share/authrail/my-deployment"
```

The status output shows the container name, whether it is running and whether
it has usable signed rules. To read the process log, use that container name:

```sh
docker logs --tail 50 YOUR_SIDECAR_CONTAINER
```

Replace `YOUR_SIDECAR_CONTAINER` with the name from setup. If the container is
running but has no usable rules, check its API connection, deployment access
and selected Rails. Keep its files and volumes while investigating; they hold
reports and recovery information as well as configuration.

## 3. Connect your application container

Inside the container, the sidecar listens at `127.0.0.1:7078`. This is a
**loopback address**, visible only to processes sharing that container’s network
namespace. Your application needs to join it; `127.0.0.1` in an unrelated
container would point back to that other container. Use the network setting
printed by setup when starting your application:

```sh
docker run --network container:YOUR_SIDECAR_CONTAINER \
  --mount type=bind,src=YOUR_PRIVATE_APPLICATION_CONFIG,dst=/run/authrail,readonly \
  YOUR_REVIEWED_APPLICATION_IMAGE
```

Replace the placeholders with the sidecar container name, the full path to
your private application configuration and your application image. That image
should contain the SDK wrapper around your business function. Mount the
adapter token, private signing key and action configuration where the
application expects them; this example uses `/run/authrail`. If a file cannot
be read, fix ownership for the application user rather than opening access
to everyone.

Keep the agent outside this network namespace and leave port `7078` private.
Business-provider credentials belong in the application, which decides when
to use them. The standard setup container publishes no ports; if your
application accepts incoming requests, work with its operator to provide the
required ingress without exposing the sidecar. Recreate application containers
when replacing the sidecar so they join its new namespace.

Use `http://127.0.0.1:7078` in the [Node](/docs/node), [Go](/docs/go) or
[Python](/docs/python) client. Run the invoice example and open its
[Action and decisions](/docs/records) to see the connection working. Use [native setup](/docs/native) when
the application runs directly on your host.

<details className="guide-details">
<summary>Stop, restart or remove the installation</summary>

Pause the protected application before stopping its sidecar. These commands
operate only the installation identified by the private directory:

```sh
./authrail-sidecar installation stop --directory "$HOME/.local/share/authrail/my-deployment"
./authrail-sidecar installation start --directory "$HOME/.local/share/authrail/my-deployment"
```

To remove the stopped container:

```sh
./authrail-sidecar installation remove --directory "$HOME/.local/share/authrail/my-deployment"
```

Both commands preserve the named volumes and local connection files. Keep
these until queued reports have been delivered and any uncertain operation
has been investigated. Removing storage to clear a warning can erase the
information needed for recovery; if a saved volume is missing, setup stops
instead of creating an empty replacement. See [recovery](/docs/recovery).

</details>

<details className="guide-details">
<summary>Reruns, upgrades and optional diagnostics</summary>

Rerun setup with the same directory to reconnect that deployment. It preserves
keys and edited SDK helpers; generated updates are saved separately for review.
Do not reuse the directory for a different deployment or silently rotate keys.

Before upgrading, pause the application and preserve both volumes and the
private setup directory. Check the SDK, Runtime image and setup executable
together in the compatibility guide. An image digest identifies its contents,
so record that value along with the version rather than relying on a tag alone.

Process logs are available without a separate monitoring service. If your
team uses OpenTelemetry, an operator-managed installation can send traces and
metrics to its Collector; see [configuration](/docs/configuration). Guided
setup has no OTLP option. Monitoring output remains separate from permission
checks, so a monitoring failure does not stop an Action.

</details>
