**AuthRail's contextual AI** helps a rule use information that needs to be read
from text. Your application uses AuthRail's SDK to ask a configured model a
reviewed question, check the answer and supply it to the rule.

For example, a support team may require human review when a customer message
asks for passwords or API keys. The rule needs an answer to “does this message
request credentials?” That answer is a **fact**: information used when deciding
whether the action may continue.

Some facts do not need a model. An application can read an invoice balance
from a trusted system. Use contextual AI when the answer requires interpreting
selected material, and a normal lookup when the source already stores the value.

## Add a credentials-request check to a support reply

This setup involves the person reviewing the rule and the developer connecting
the application. The reviewer decides what question is appropriate; the
developer controls the source text and the model call.

### 1. Choose the question and the text it needs

Use a question with an answer the rule can check, such as a Yes/No answer to
whether the customer message requests credentials. Select the customer message
needed for that question, rather than sending an entire ticket and every
attachment.

**The selected text goes to the configured model provider.** Decide which
fields may leave the application and which provider and account may receive
them. Remove unnecessary fields and redact protected values in trusted
application code before the model call where your disclosure policy requires it.
The extractor does not automatically remove every protected value. If the
material cannot be shared safely, do not send it.

### 2. Review the source setup with the rule

Record the source, the expected answer, the model and instructions, the required
confidence, and what should happen if the answer cannot be obtained. AuthRail
saves the reviewed setup as a **Context Source Version**. The rule selects that
saved version so the application uses the setup that was reviewed.

### 3. Connect the application's fact reader

The developer uses a matching SDK extractor—the helper that sends the selected
text and question to the model. The application checks the answer's format and
confidence, signs the answer with its source information, and reports that fact
to AuthRail. The fact report contains the answer and source information rather
than the selected raw text.

Your application owns the model credential and the choice of source fields.
The agent must not choose another provider URL, switch accounts or supply its
own credential for this check.

### 4. Compare ordinary and sensitive requests

Connect the fact to the rule that requires review, then try an ordinary customer
message and one asking for credentials. Also test an unavailable or uncertain
answer. Inspect the Action's decision and source status.

The expected result is a typed answer the rule can use, with enough source
information to explain where it came from. A positive credentials answer can
require review before the protected send function runs. The model's answer
supplies context; it does not itself give permission to send a reply.

See [Rails](/docs/rails) for rule authoring and [Actions and decisions](/docs/records)
for reviewing the result.

<details className="guide-details">
<summary>More about ordinary lookups and model answers</summary>

| Question | Source | Example answer |
| --- | --- | --- |
| What is the invoice's remaining balance? | Reviewed QuickBooks invoice lookup | A number such as `80`. Currency needs its own reviewed source. |
| What is the invoice's status? | Reviewed Stripe invoice lookup | The status from the selected invoice and account. |
| Does the customer message ask for credentials? | A configured model reading that message | `true` or `false`, with the required confidence. |

Other model questions can return a category or a score. The returned value must
match the shape expected by the rule; a free-form explanation cannot replace
its required Yes/No answer.

A fact reader performs a read. It must not execute the payment or message being
checked. Provider credentials, OAuth consent, refresh and revocation belong to
the application. A compliance Connection does not grant Runtime permission to
change provider records.

</details>

<details className="guide-details">
<summary>More about source trust and missing answers</summary>

A Context Source Version also records the provider account and resource, the
expected value type, how long the answer remains fresh and how failures are
handled. If the source or model setup changes, review and publish a new version.
Use that version's account and resource lookup in application code.

A timeout or unavailable provider means the fact is unavailable. A wrong
account, wrong resource or invalid value is untrusted. Neither is a passing
answer. Do not replace an unread balance with zero or an uncertain sensitivity
answer with false. Follow the configured denial or review behaviour while
repairing the source.

A refusal or insufficient model confidence leaves an uncertain answer. A later
check of the answer cannot undo source text already disclosed to the provider.
Keeping text out of AuthRail's fact report does not keep it out of that model.

</details>

<details className="guide-details">
<summary>More about model identity and earlier actions</summary>

The fact's source details identify the model used to read the text. That model
can differ from the model configured in AI Inventory and from the model that
produced the agent's request. Configuration alone does not prove which model
ran the agent.

Rules that depend on earlier actions need history from the application's
trusted saved session state. An agent's claim that someone approved an action
previously cannot replace an authenticated approval record. Keep raw provider
bodies, credentials and source text out of diagnostic logs.

</details>
