**AuthRail Contextual AI** helps a rule understand meaning. For example, a rule
can stop a code change that weakens authentication, send a confidential export
for review, or check whether a proposed response discloses private information.

You enable it on the Rail that needs that understanding and describe the rule.
AuthRail prepares the assessment for you to review. Your application sends only
the permitted fields to AuthRail; AuthRail returns a bounded answer, and the
local sidecar applies your published rule. You do not configure a model, supply
a model API key or write an extractor.

A model answer supplies information. It cannot approve an action, override a
denial or replace a person's required approval.

## Decide whether the rule needs interpretation

Use a trusted lookup for a value already stored in a business system. Use
Contextual AI when the rule needs to understand selected text.

| What the rule needs | How to obtain it |
| --- | --- |
| An invoice's remaining balance | Read the exact invoice from a trusted account. |
| Whether a proposed code change weakens authentication | Ask AuthRail Contextual AI to assess the selected diff. |
| Whether an export contains confidential business information | Assess the permitted document fields before exporting. |
| The purpose expressed in a payment justification | Classify the selected justification into the reviewed categories. |

A missing balance, unknown caller or expired approval is not a question for
Contextual AI to guess. Those checks keep their own failure behaviour.

## Prepare a contextual Rail

Suppose your application has a protected function that applies a code change.
Its reviewed action includes a text input named `diff`. You want to block a
change that removes authentication checks.

1. Open the action's Guard Rail draft. Turn on **AuthRail Contextual AI**.
2. Describe the boundary, for example: “Block code changes that remove or weaken
   authentication checks.” Choose **Prepare contextual checks**.
3. Review the proposed assessment and rule. Check what it asks, which input or
   result fields may be sent to AuthRail, and how its answer affects the rule.
4. Add examples with a usable answer and with a missing or uncertain answer.
   Test the draft and review the results before publishing the exact version.
5. Select that published version for the application's deployment, following
   [Rails](/docs/rails).

For this example, an assessment might ask whether the selected diff weakens
authentication. A Yes answer matches the denial rule. A No answer clears that
check; the other selected rules still have to permit the operation. An uncertain
answer does not clear it.

Choose a **Policy Rail** when the rule comes from a published organisational
Policy, including a rule that requires human approval. Its contextual setting
uses the same review of the question and permitted fields. Changing the toggle
or assessment changes the draft; the revised version must be tested and published.

## What your application does

Keep the SDK around the function that actually owns the operation, as shown in
the [Node.js](/docs/node), [Go](/docs/go) or [Python](/docs/python) guide. The SDK
obtains the selected Rail's requirements from the sidecar and handles the
contextual request. Your application supplies the reviewed input and trusted
caller/resource identity. It keeps its business credentials.

There is no separate contextual model client to initialise. These excerpts use
an already configured SDK client and reviewed `operation`. The change service
and recovery journal are application code: the journal saves execution context,
and the service uses the SDK's stable idempotency key to prevent duplicate effects.
Handle blocked requests and uncertain outcomes using [recovery](/docs/recovery).

<Tabs items={['Node.js', 'Go', 'Python']} groupId="sdk-language" persist>
<Tab value="Node.js">

```ts
const checked = await client.enforce(operation, { diff },
  async (input, execution) => {
    await journal.saveRecovery(execution);
    return changes.apply(input, {
      idempotencyKey: execution.providerIdempotencyKey,
    });
  });
```

</Tab>
<Tab value="Go">

```go
type Change struct { Diff string `json:"diff"` }
type ChangeResult struct { Applied bool `json:"applied"` }

result, callCheck, resultCheck, err := authrail.Enforce(ctx, client,
    operation, Change{Diff: diff},
    func(ctx context.Context, input Change,
        execution authrail.ExecutionContext) (ChangeResult, error) {
        if err := journal.SaveRecovery(ctx, execution); err != nil {
            return ChangeResult{}, err
        }
        return changes.Apply(ctx, input, execution.ProviderIdempotencyKey)
    })
```

</Tab>
<Tab value="Python">

```python
async def apply_change(checked, execution):
    await journal.save_recovery(execution)
    return await changes.apply(
        checked, idempotency_key=execution.provider_idempotency_key
    )

checked = await client.enforce(operation, {"diff": diff}, apply_change)
```

</Tab>
</Tabs>

In Enforce, the function does not run until the SDK establishes permission and
records its start. A result-time contextual check happens after the function;
it can withhold the result but cannot undo the effect.

## Follow the request

1. The sidecar identifies the assessment required by the selected published Rail.
2. The SDK selects only its permitted fields and checks any required local
   processing before sending them through the sidecar to AuthRail.
3. AuthRail interprets that material and returns a signed Yes/No answer, category
   or score, or reports that it could not obtain a usable answer.
4. The sidecar verifies that the finding belongs to this exact request, caller,
   input, phase and Rail version, then applies the deterministic rule.
5. The SDK applies the decision at the protected function or result boundary.

When Contextual AI is off for a Rail, that Rail causes no contextual request.
A timeout, refusal or uncertain answer never becomes a made-up No answer. The
rule cannot rely on a missing finding as if the check passed. Repair the cause
or obtain a fresh check; do not weaken the rule simply to make it proceed.

## Know what leaves your application

**AuthRail receives the selected contextual material.** Review that disclosure
when publishing the Rail. Select only the fields needed for the question and
apply required filtering before the contextual call. A later answer or result
check cannot undo information already sent.

Selected text is processed for the assessment; it is not added to normal logs,
traces or retained Actions. The retained decision includes the assessment's
identity, status and bounded finding. Keep raw text and credentials out of your
application's diagnostic logs too.

Contextual AI interprets material through AuthRail's service. It does not prove
that an answer is correct, identify which model generated the original agent
request, or provide universal protection against sensitive-data disclosure.
Inspect the resulting [Action and decisions](/docs/records) alongside your
application's own effect and recovery records.
