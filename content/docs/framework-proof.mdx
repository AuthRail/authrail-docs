Runtime records can help you check whether a Control worked in a connected
application. Suppose a Control prevents an assistant from paying an invoice
outside its permitted account. An **AI actions Test** can inspect saved requests
for that operation and check whether they were denied before execution.

The Test gives the records a question and a period. One allowed request cannot
establish how the Control worked throughout a month, and an empty history
cannot show that it was exercised. If your application has not produced any
records yet, start with [the quickstart](/docs/getting-started).

## Open the Control that addresses the duty

In <a href={AUTHRAIL.clientOrigin}>AuthRail</a>, open the active Framework and find the applicable duty under **Obligations**.
Read its coverage and open the mapped Control's **Tests and Evidence** area.
This keeps the check associated with the practice and version your organisation
has agreed to rely on.

<ProductShot src="/screenshots/framework-obligations.jpg" alt="Framework Obligations with applicability, coverage and View coverage actions" caption="Start with the duty and follow its coverage to the Control you want to check." />

If that relationship has not been established, follow
[Frameworks and scope](/docs/frameworks) and
[Policies and Controls](/docs/policies-controls) first. You can reuse the same
organisation Control where it supports several Frameworks.

## Describe which requests to check

In the Control draft, choose **Add test**, then **AI actions**. Select the
**AI system**, its **Enforce deployment** and the **Action to check**. For the
out-of-account payment example, set **Required outcome** to **Denied before
execution**. A Test checking completed work can instead use **Completed
execution**, which refers to the application's completion report.

Set **Minimum Actions** to the number of matching records the check needs.
This prevents an empty or insufficient set from satisfying the Test. Continue
to **Passing criteria**, give the Test a name and explain what the records must
demonstrate. Under **Schedule**, choose the cadence and how long each result
remains current. Select **Add Test** and complete the Control's approval process
before recording results against it.

<ProductShot src="/screenshots/framework-tests-evidence.jpg" alt="A Control's Tests and Evidence area with a quarterly check and its result history" caption="The approved Test describes the check. Its results record what was found in each review period." />

### Work through a retained-record check

Northstar's [account-change review](/docs/tests-evidence) needs more than a
terminal execution state: a person must reconcile the application history and
inspect approval timing. Keep that human check. An **AI actions** Test can add a
separate, narrower check of requests that a rule must block, such as attempts to
change an account outside the application's permitted boundary.

In a Control draft, configure that narrower Test as follows:

| Choice | Example selection and reason |
| --- | --- |
| AI system | The confirmed support assistant in AI Inventory. |
| Enforce deployment | The installation that actually protects the support application's function. |
| Action to check | Its reviewed out-of-account access-change operation, whose selected Rail must deny these requests. |
| Required outcome | **Denied before execution**. |
| Minimum Actions | `2`, because this check requires at least two retained matching requests. |
| Procedure | Inspect every matching retained request in the completed period; require denial without execution, and compare the application's account-change history for bypasses. |
| Schedule | Repeat every `30` days; results stay current for `45` days in this example. |

Use an operation/deployment selection that represents the denied behaviour you
intend to test. The check evaluates all matching retained Actions in that period,
not a hand-picked pair: a selection containing ordinary successful changes would
not satisfy an expectation that all were denied. If your current operation
selection mixes different intended outcomes, use the person-led Test to assess
them rather than describing an unsupported input filter.

Approve the Control Version containing this definition and review any Mapping
replacement needed to use that version. Then choose a completed period containing
the two requests. Both need a retained denied call or rejected approval and no
executor receipt. One missing record does not meet a minimum of two; an Observe
denial does not establish that the function was stopped. The selected period
must contain the first reported call of each qualifying Action, so a later result
arriving within the period does not move an older request into it.

## Review the period and save your conclusion

Choose **Record Test result** and enter the completed **Review period**. Inspect
**Retained Runtime Actions**, the matching records AuthRail has saved for that
period, and open their decisions and execution reports. Record what you
reviewed and choose the outcome, then select **Save Test result** or the combined
Evidence submission action when required. **History** shows the saved result.

AuthRail checks those records against the Test's expectation; selecting a
passing label does not replace the check. If records are missing or an outcome
is unknown, investigate the gap or record the appropriate result. Observe
records show what rules would decide and cannot demonstrate that Enforce
stopped an operation.

When the Control requires human review, inspect the approval and the request it
authorised. **Allowed** alone establishes neither that a person approved the
request nor that the operation ran. **Completed execution** describes what the
application reported. For independent confirmation of an external effect,
inspect the matching provider record. A signed Decision Certificate or
attestation helps establish the integrity of its record rather than proving the
provider effect.

A saved Runtime-linked Test result preserves the record references used for the
conclusion. It does not automatically satisfy every Evidence requirement on the
Control. If a requirement expects this Test result, select it through **Select
Test result**, submit the correct completed period and finish the requirement's
acceptance flow. A requirement expecting the October review file must instead
receive that file package. Changing source type to avoid the required material
would change the definition of the check.

## Follow the result into the assessment

Return to the Framework's **Readiness** and open the affected duty. The Test
result can contribute when it satisfies the accepted Mapping's expectations;
the Control may also require other proof. Follow
[Tests and Evidence](/docs/tests-evidence) to submit a document, provider record
or other source for the appropriate requirement and review.

<ProductShot src="/screenshots/framework-readiness.jpg" alt="A sample Framework showing one ready obligation out of 217 and a Not ready assessment" caption="Readiness uses the qualifying proof for each duty, so one successful check does not make the whole Framework ready." />

Attaching an Action link does not replace that proof relationship or let you
set the readiness score. For a missing or failed check,
[readiness and remediation](/docs/readiness) explains how to follow the problem
through Findings, Tasks and any eligible Exception while preserving its history.
