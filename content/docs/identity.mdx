When your application asks AuthRail to check a tool call, the request needs to
identify the installation, the caller and the record being used. These answers
come from different places. A **deployment** identifies one installation of
your AI system; your application authenticates the caller and looks up the
record. A signing key lets the application show that it supplied those details.

For example, a billing service can request an invoice check for a signed-in
staff member without giving the agent the service’s Stripe credential. This
page explains the connection files and the application’s responsibilities.
For a new installation, [guided setup](/docs/getting-started) creates the files
and registers the public key for you.

## Find the generated connection files

Setup saves files in the directory you choose with `--directory`. The
quickstart uses `$HOME/.local/share/authrail/my-deployment`. Your application
operator should own this private directory and keep it across restarts, because
it contains the keys and credentials needed to reconnect the same installation.
The table shows which process needs each file; token values and private keys
should stay out of chat, browser code and shared terminal output.

| File | Who uses it | Purpose |
| --- | --- | --- |
| `connection.json` | Operator and application configuration. | API URL, organisation/deployment IDs, trusted AuthRail signing fingerprints and the application's public-key fingerprint. JSON keys use camelCase, including `organisationId` and `deploymentId`. |
| `deployment-token` | Sidecar. | Connect this deployment to AuthRail for configuration and reports. |
| `adapter-token` | Protected application and sidecar. | Authenticate local SDK requests. |
| `executor-private.pem` | Protected application only. | Sign the application’s requests and execution reports. |
| `executor-public.pem` | AuthRail registration and sidecar. | Verify the application's signatures; this is the only application key sent to AuthRail. |

A **fingerprint** is a short identifier for a key. The AuthRail signing
fingerprint lets the sidecar recognise rules issued by AuthRail. Your
application’s fingerprint identifies the key it uses to sign requests. Keep
these two values distinct, and keep business-provider credentials separately
in the application that performs the work.

The setup command's Docker and native paths have different placement and
lifecycle instructions. Follow [Docker](/docs/docker) or [native](/docs/native)
for the selected path, and use the [configuration reference](/docs/configuration)
when provisioning through your deployment's secret store.

## Bind a trusted caller and target

Your application should authenticate the user or service before asking the
sidecar for a decision. It then supplies that caller and session as
`principalId` and `sessionId`, and looks up the target record before supplying
`resourceId`. The SDK uses the same information in each supported language.

Suppose an agent requests invoice `in_example`. The application first checks
which account the user may access and finds the invoice in that account. It
chooses the provider credential and the confirmed Operation Version for the
function, then signs the request. This keeps the agent’s requested input
separate from the identity and access established by your application.

Use a stable business request key so recovery can recognise the same work.
The signature shows that the registered application key supplied the request;
it does not independently establish the caller’s identity or a provider effect.
That is why authentication, resource lookups and provider verification remain
part of your application.

<summary>Manual provisioning for an existing deployment</summary>

If your team provisions credentials through an existing secret store or
deployment tool, it can prepare the equivalent files and settings below.
Guided setup normally handles this work. For an existing installation, reuse
its registered key and credentials unless you are carrying out a planned change.

### Copy the deployment settings

In <a href={AUTHRAIL.clientOrigin}>your AuthRail workspace</a>, open the deployment
and **Integration setup → Configure the sidecar**. Copy these values into your private deployment
configuration:

- **AuthRail URL:** <a href={AUTHRAIL.apiOrigin}>{AUTHRAIL.apiOrigin}</a>, the API address the sidecar connects to.
- **Organisation ID:** the organisation that owns this setup.
- **Deployment ID:** the installation you are connecting.
- **Trusted signing key:** identifies the AuthRail key that signs your rules.
  Copy it from this authenticated setup page, not from an arbitrary downloaded
  file. If the page shows two fingerprints during a key change, keep both as
  the comma-separated value shown there.

### Save the deployment token

Create a private directory outside your source checkout. These examples use a
POSIX terminal on macOS or Linux:

```sh
umask 077
mkdir -p "$HOME/.local/share/authrail/my-deployment"
chmod 700 "$HOME/.local/share/authrail/my-deployment"
```

In **Get a deployment token**, select **Create token**. AuthRail shows the new
value once. Using your private editor or secret-provisioning tool, save that
value in this file:

```text
$HOME/.local/share/authrail/my-deployment/deployment-token
```

The sidecar uses this credential to fetch the deployment’s rules and send
reports. Store it privately, and remember that **Replace token** invalidates
the old value. AuthRail does not display a saved token again.

### Create the application's key and local token

The application signs its requests so the sidecar and AuthRail can check where
they came from. OpenSSL creates two related files: a **private key** the
application keeps, and a **public key** you register in AuthRail.

With OpenSSL that supports Ed25519, run:

```sh
umask 077
openssl genpkey -algorithm Ed25519 -out "$HOME/.local/share/authrail/my-deployment/executor-private.pem"
openssl pkey -in "$HOME/.local/share/authrail/my-deployment/executor-private.pem" -pubout -out "$HOME/.local/share/authrail/my-deployment/executor-public.pem"
openssl rand -hex 32 > "$HOME/.local/share/authrail/my-deployment/adapter-token"
```

The last command also creates an **adapter token**. Your application and local
sidecar share this separate secret to authenticate their local connection.
It is different from the deployment token.

Run these commands once for a new installation. If you already registered a
key, use its existing files; overwriting them would break that registration.

### Register only the public key

Print the public file:

```sh
cat "$HOME/.local/share/authrail/my-deployment/executor-public.pem"
```

Copy the complete PEM text into **Integration setup → Connect your application
→ Application public key**, then select **Connect key**.

Only the public key goes into AuthRail. The matching `executor-private.pem`
stays with your application, alongside its other private credentials and
outside the agent’s reach.

### Use the files in the right place

The **sidecar** needs `deployment-token`, `adapter-token` and
`executor-public.pem`. The **application SDK** needs the same `adapter-token`
and `executor-private.pem`. Give both the organisation and deployment IDs.
The SDK also needs the reviewed Operation Version ID copied from **Connected
actions**.

The files can be supplied by a private secret store or Secrets Manager in a
deployed application. Do not put their contents in Git, browser code, agent
prompts or shared terminal captures.

Continue with [Docker setup](/docs/docker) or [native setup](/docs/native). The
[configuration reference](/docs/configuration) lists the setting names used by
each process.

<details className="guide-details">
<summary>How these identities differ</summary>

**The AI system and deployment.** AI Inventory records the system your
organisation governs. A deployment is one installation of it. A configured
provider or model describes that setup; it does not prove which model handled
an individual request.

**The two signing keys.** AuthRail's trusted signing fingerprint identifies the
key that signs your selected Rails. Your application's public key verifies
requests signed by its private key. These keys have different jobs; do not
substitute their fingerprints.

**The caller and target record.** The application obtains `principalId` and
`sessionId` from an authenticated user or service context. It resolves
`resourceId` through its own lookup. The SDK examples show how to supply these
values; an agent's statement about its identity or target does not authenticate
it.

</details>

<details className="guide-details">
<summary>Changing keys or using discovery</summary>

**Application-key changes.** Use **Change application key** to register the new
public key before switching the application and sidecar. During the displayed
overlap, configure the previous public PEM in the sidecar too. Check every
sidecar's pending and blocked reports before retiring the old key. AuthRail
cannot inspect those private local queues for you.

**AuthRail signing-key changes.** Integration setup can display two trusted
fingerprints during a transition. Use both displayed values until that
transition is complete. The sidecar also checks that configuration belongs to
the intended organisation and deployment, is valid for this time, and is not
older than configuration it has already accepted.

**Optional discovery.** A tenant manager can create a short-lived setup key.
SDK discovery uses it to find or propose the AI Inventory item. Review and
confirm that identity before Enforce. A discovery key is not the deployment
token or permission to perform a business action.

Preserve the full sidecar state directory through key changes and restarts.
If a state file is invalid, follow [recovery](/docs/recovery) so you can
investigate it without losing queued reports or configuration history.

</details>
