AuthRail is an AI governance platform that helps organisations decide what their
AI agents are allowed to do, apply those decisions when an agent uses a tool,
and understand the outcome afterwards. It connects the rules your organisation
sets with the applications where agents read information, make changes and
carry out business tasks.

As agents move beyond answering questions, they can take on responsibilities
that affect customers, software and the organisation itself: building an
application, releasing changes to production, changing account access, exporting
confidential information or committing company funds. These tasks need more
than access to a tool. They need rules about who may request the work, which
systems and information it may affect, and when a person must review it.

AuthRail helps you express those boundaries in the applications you connect.
You can introduce it while building an agent application, or add it to an
existing workflow, so authority is considered alongside the tools and business
functions rather than left to the model's judgement.

## From an organisation's rule to an agent's action

Consider an engineering assistant helping a team build and maintain an
application. Preparing a code change, accessing production data and releasing
that change are different responsibilities. The team might allow work in a
preview environment, require human review before a production release, and
stop a request that would expose credentials or remove an authentication check.
A customer-service application could use the same approach for changes to
customer access, and a finance application for payments or refunds.

Those rules need information from the application: the person requesting the
work, the system or environment involved, the proposed change and any business
facts the decision depends on. Your integration establishes which functions
pass through these checks; AuthRail does not become a cloud executor or gain
access to those systems simply because you describe a rule.

In AuthRail, you express these rules through **Rails**. When the assistant asks
to use a connected tool, AuthRail **Runtime** checks the request against the
published Rails. The application can proceed when the request is permitted,
stop when it is denied, or save it while a person reviews it. Runtime can also
check the tool's result before it is returned to the assistant, for example to
withhold an API key while still returning useful application settings.

The [video walkthrough](/docs/application-example) shows this in a connected
agent application. The [Rails guide](/docs/rails) explains how to prepare rules
for your own actions, including rules that need a trusted business value or
AuthRail Contextual AI to interpret selected material.

## Connecting your application

Your application continues to perform its business operations and hold the
credentials they need. A developer adds an AuthRail **SDK** around the function
that performs each operation, and runs a **sidecar** beside the application to
evaluate its Rails. Placing the check at that function is what allows Runtime
to stop an operation before it runs; connecting an agent account or installing
a library alone does not cover its other tools.

If you are building an agent application, [the app-builder guide](/docs/build-your-app)
explains how the model's tool request reaches this check and which information
comes from your application. The [quickstart](/docs/getting-started) introduces the SDK through a small
read-only example in Node.js, Go or Python, which you can then adapt to the
functions in your application. It begins in
**Observe**, where you can see what the rules would decide while the function
continues, before moving to **Enforce**, where the connected function requires
permission to run.

You can also use [AuthRail MCP](/docs/mcp) to work with AuthRail through an
assistant. With your organisation's permissions, a coding assistant can help prepare
actions and rules, obtain SDK integration guidance and inspect the resulting
records. It uses its separately authorised development tools to work on your
application code. Publication and
approval still require an authorised person's decision, and the business tools
still need their Runtime integration.

## Understanding what happened

AuthRail brings a request's decisions, approvals and application reports together
in an **Action**. This gives you a way to investigate why work was stopped,
which rules applied, and what the application reported after it was allowed
to continue.

Permission and outcome answer different questions. An allowed refund request
may still be rejected by the payment provider, while a lost response may leave
the outcome uncertain. The Action preserves those distinctions so you can
compare the application's report with the provider's own record and resolve
uncertainty before trying the operation again. [Actions and records](/docs/records)
explains how to read that history.

## Connecting agent oversight to governance

The same organisation may need to show that its practices meet the duties of a
regulation or standard. AuthRail supports that work through Policies, reusable
Controls, Frameworks, Tests and Evidence. A Policy describes an expectation, a
Control explains how the organisation fulfils it, and the Control's Tests and
Evidence establish whether the practice worked during the period under review.

Runtime records can contribute to that assessment when the relevant Test or
Evidence requirement defines how they should be used. [Framework readiness](/docs/readiness)
then follows the applicable duties and their reviewed proof; it is not created
simply by collecting logs or allowing an agent request. You can explore this
connected workflow in [Policies and Controls](/docs/policies-controls) after
getting familiar with Runtime.
