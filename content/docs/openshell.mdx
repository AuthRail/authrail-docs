<a href={AUTHRAIL.references.openshell}>NVIDIA OpenShell</a> runs an agent in a
sandbox: an environment with restrictions on files, processes and network access.
AuthRail checks the business operations your application performs for that agent.
Together, they let an agent do useful work through a controlled route while
keeping its access to the surrounding system limited.

For example, an engineering agent could prepare a release inside OpenShell and
ask your release service to deploy it. OpenShell would restrict the agent's file
and network access, while AuthRail would check the requested application,
environment and approval before the release service uses its deployment
credential. The service holds that credential outside the agent's sandbox.

## Choose this integration when you operate the agent

Use OpenShell when you or your team run the agent workload and can configure its
execution environment. It is optional: your application can use AuthRail without
running an OpenShell sandbox. Connecting an assistant to AuthRail does not install
OpenShell around that assistant's hosted chat service.

The application containing your business functions runs outside the sandbox,
with an AuthRail SDK and its sidecar. The agent reaches that application through
an authenticated entry point; the application checks permission before calling
the provider or changing your data.

```text
Agent in OpenShell → your application → business system
                            ↕
                   AuthRail SDK and sidecar
```

The SDK follows the language of your application. An agent in the sandbox can
call a service written in Node.js, Go or Python; it does not need to use the same
language as the service. The existing OpenShell-specific reference implementation
is Node.js. Go and Python use their own SDK integration and require your service
to implement the sandbox identity, authentication and recovery boundary described
below; there is no automatic OpenShell wrapper for those languages.

## 1. Protect your application's function

Start with the function that performs the work, such as `deployRelease`,
`changeCustomerAccess` or `readCustomerRecord`. Follow
[Building your own application](/docs/build-your-app) to describe its inputs and
results, bind the caller and account from trusted application context, and wrap
the function with the SDK. Use the guide for your service's language:

| Application language | Integration guide |
| --- | --- |
| JavaScript or TypeScript | [Connect a Node application](/docs/node) |
| Go | [Connect a Go application](/docs/go) |
| Python | [Connect a Python application](/docs/python) |

Connect the sidecar using [Docker](/docs/docker) or [native setup](/docs/native).
Keep the provider client and credential inside the application process or its
private execution service. The sandbox needs permission to request a business
operation, rather than possession of the provider credential itself.

In <a href={AUTHRAIL.clientOrigin}>AuthRail</a>, review the operation and publish
the Rails for it. For the release example, a Policy Rail could require an assigned
reviewer's approval for production releases, while a result Guard could restrict
which fields the agent receives afterwards. Choose protections your installed
SDK and sidecar support; [compatibility](/docs/compatibility) explains the released
capability boundary.

## 2. Give the sandbox one authenticated route

Expose only the application entry points the agent needs. Your application's
authentication must identify the calling sandbox and resolve its permitted user
or workload, organisation, deployment and operation. An agent-supplied account ID
or sandbox name is not sufficient proof of that identity.

Give the sandbox a credential limited to its application access. Keep provider
credentials, the SDK's adapter token, signing keys and recovery storage outside
the sandbox. A caller allowed to request a release should not also be able to
select another deployment's credentials or replace the operation being checked.

Use HTTPS when the request crosses a network boundary, with a certificate trusted
by both the sandbox client and OpenShell's network supervisor. The sidecar remains
on the application's private network; it is not the endpoint exposed to the
agent. [Identity and deployment](/docs/identity) explains the separate application
and workload identities.

## 3. Restrict the agent's environment

Install and operate OpenShell using the
<a href={AUTHRAIL.references.openshell}>NVIDIA documentation</a>. Review a policy
for your own agent image, executable and application address. It should allow the
agent to reach its authorised application route and any separately approved model
or development services, while keeping the application's private files and
credentials inaccessible.

For the release service, allow the application route that requests a release;
keep direct cloud deployment endpoints and host administration sockets outside
the agent's access. Otherwise the agent could bypass the function you wrapped.
Review filesystem, process and network restrictions together, including any rules
added by OpenShell provider configuration.

If your application relies on a particular sandbox policy for protection, bind
that requirement to the running sandbox's identity and effective policy. Check
that the required restrictions are loaded before accepting work and again when
resuming a saved request. A reused sandbox name or a policy file on disk does not
establish that the running sandbox has those restrictions. The reference
implementation linked below shows this containment check for OpenShell 0.1.6.

## 4. Handle the decision and returned result

The application sends the operation through its AuthRail SDK. With Enforce enabled,
a denial stops the function before it runs, and an approval-required decision
leaves the original work saved for an authorised reviewer. After approval, the
application resumes that request with its original identity and execution context;
the agent cannot provide its own approval.

When the function completes, the SDK applies the configured result checks before
releasing information back to the sandbox. Withholding a result does not undo a
business operation that already happened. If a provider times out after accepting
a write, retain its original reference and use [recovery](/docs/recovery) to
establish the outcome before another attempt. [Human approvals](/docs/approvals)
explains the saved-request lifecycle.

Your application owns an authenticated continuation workflow for its users or
operators. Keep approval and recovery records across restarts, and prevent repeated
requests from creating repeated effects. These responsibilities apply whether
your application uses Node.js, Go or Python.

## Check the complete access path

From the running sandbox, exercise one permitted operation and one operation its
Rails deny. Check that the allowed function runs, the denied function does not,
and the sandbox cannot reach the provider or read the application's private
credentials through another route. For approval-required work, confirm that the
saved request resumes through the application after the named reviewer decides.

Inspect the Action in AuthRail alongside your application's execution record and,
where applicable, the provider's own record. Permission, reported completion and
independently established effects answer different questions. OpenShell's access
restrictions and AuthRail's business checks must both cover the path you intend
to protect; installing either component does not secure unrelated tools.

<summary>OpenShell 0.1.6 reference implementation</summary>

The sidecar repository includes a
<a href={`${AUTHRAIL.repositories.sidecar}/tree/v0.2.0/integrations/openshell`}>Node.js OpenShell integration</a>
with an authenticated HTTPS entry point, sandbox/policy inspection, SDK call and
result checks, and saved approval/recovery handling. It is a source integration
reference, not a separate installer or a prerequisite for using AuthRail.

That implementation targets OpenShell **0.1.6**, sidecar source **v0.2.0** and
Node SDK source **v0.1.1**. Its example uses Node **22.13 or newer** and links a
sibling SDK checkout. The accompanying demonstration callback writes a simulated
value to local SQLite; it performs no payment or other provider operation.
Use the implementation to understand the boundary, then supply your own business
function and its provider idempotency and reconciliation behaviour.

Its source README owns the certificate, private file, policy and state-directory
settings needed to run that reference. The application checks the immutable
sandbox identity and effective policy rather than trusting caller assertions.
Its continuation and reconciliation functions are operator-facing; it does not
provide a sandbox-accessible resume endpoint. A production service must supply
its own authenticated continuation experience.

When changing OpenShell versions, verify the supported policy schema, effective
restrictions and containment inspection against NVIDIA's documentation for that
version. Keep the application's saved requests and required sidecar state intact
through restarts and upgrades.
