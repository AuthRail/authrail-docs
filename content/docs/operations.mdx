When a request stops unexpectedly or its decision has not appeared in AuthRail,
start with the application's connection and follow the request from there.
The deployment page tells you whether its sidecar is communicating; the Action
explains the business decision; local logs help the operator find a process or
delivery problem.

A **deployment** is one configured installation of your AI application. Its
**sidecar** runs beside it to evaluate the selected Rails. **Connection health**
describes that process and its reporting, rather than the governance Health
of a Control. You can use these checks without setting up a separate monitoring
service.

## Check the connection

1. In <a href={AUTHRAIL.clientOrigin}>AuthRail</a>, open **AI Inventory** and choose the AI system and open the deployment.
2. On **Overview**, find **Connection health** and its last update time.
3. Choose **Check again** and read any message about rules or reports waiting
   for delivery.

A recent update shows that the installation is communicating and helps you
check whether it has usable rules. If the update is old, the sidecar operator
can check the process, network and deployment credential. Communication alone
does not establish that every application tool uses the SDK; that is part of
the [execution-access review](/docs/security).

## Follow one request

In the deployment's **Actions & decisions**, open **Connection log**. Find the
request event and choose **View related action**. If the application supplied
a business request key, use **Find an exact action key** to locate it directly.
Then follow the Action's checks, approval and **What the application reported**.

<ProductShot src="/screenshots/runtime-connection-log.jpg" alt="Deployment connection log with a View related action link beside an event" caption="Open the related Action to move from a diagnostic event to the request's decision and execution reports." />

This lets you explain what the rules decided and what the application reported.
To confirm a provider effect independently, compare it with the provider's own
record. An uncertain effect needs [recovery](/docs/recovery) before another
write. If the log cannot refresh, restore its connection and try again rather
than treating the older list as a current view.

## Read the sidecar's local output

The sidecar's output is useful when the process or delivery path needs
investigation. Guided native setup writes `sidecar.log` in its private setup
directory; a foreground process uses its terminal, and an operated service
uses its service manager's output.

For guided Docker setup, replace `YOUR_SIDECAR_CONTAINER` with the container
name printed by setup:

```sh
docker logs --tail 50 --follow YOUR_SIDECAR_CONTAINER
```

For the native quickstart, use your own `--directory` location:

```sh
tail -n 50 -f "$HOME/.local/share/authrail/my-deployment/sidecar.log"
```

Native Runtime 0.2.0 and the separately published 0.2.0 image write structured
`decision` and `execution_report` events, with references to the related Action.
The guided Docker installer selects Runtime 0.1.0, whose output does not include
this event stream. Use its local health and central Action records instead;
[compatibility](/docs/compatibility) explains the version difference.

Press **Ctrl+C** when you finish following the output; this stops the log viewer
while the sidecar keeps running. Local logs omit business arguments, source
text, provider responses and credentials. Your operator manages their capture,
rotation and retention.

<details className="guide-details">
<summary>Read local health and understand log events</summary>

On the native sidecar's host, request its local health:

```sh
curl --fail --silent --show-error http://127.0.0.1:7078/health
```

The response describes its **bundle**, the signed collection of rules and
settings from AuthRail. `bundleValid: true` means the loaded configuration is
valid and unexpired. Compare `mode` with the deployment's selection, and check
`pendingReports` for waiting delivery and `blockedReports` for reports needing
operator review. Preserve those reports during investigation.

In Docker, use the installed container's health command:

```sh
docker exec YOUR_SIDECAR_CONTAINER /usr/local/bin/authrail-container health
```

It exits `0` when the loaded bundle is valid and `1` otherwise, without printing
JSON. Its listener is inside the container's private network namespace; the
[Docker guide](/docs/docker) explains how the application reaches it.

Runtime 0.2.0's structured events have these meanings:

| Event | Meaning |
| --- | --- |
| `decision` | A call or result check, with its mode, outcome and recording status. |
| `execution_report` | The application reported starting an attempt or its completion, failure or uncertainty. |
| `report_delivered` | AuthRail acknowledged a queued report. Delivery does not resume a waiting action. |
| `check_unavailable` | The sidecar could not establish trusted request history. |
| `request_completed` | A local SDK request finished. Its HTTP status is separate from the rule's outcome. |

A `retained` report reached AuthRail; a `queued` report is waiting locally.
Logs themselves are best-effort diagnostics and may lose entries when their
queue fills or output fails. Where available, `logDrops` counts those losses.
Durable Actions and report queues serve separate purposes, so preserve
recording-gap files rather than rerunning an operation to recreate its log.

Authorised users can also choose a date range and export the workspace's
Connection log. Deleting diagnostic logs leaves Actions, decisions, approvals
and execution receipts under their own retention rules.

## Diagnose the symptom you are seeing

The sidecar's hosted API address is <a href={AUTHRAIL.apiOrigin}>{AUTHRAIL.apiOrigin}</a>.
Use <a href={AUTHRAIL.clientOrigin}>{AUTHRAIL.clientOrigin}</a> to inspect the
deployment in your browser. The workspace URL is not the sidecar's API setting.

Start with the same business request and its saved Action key. Keep the original
reports and application recovery state while investigating; recreating a payment
or release to obtain a cleaner log can create a second effect.

| Symptom | What it may mean | Next useful check |
| --- | --- | --- |
| The application gets connection refused before any rule decision. | Its sidecar process is stopped, the URL is wrong, or the application is in a different network namespace. | Check the process output and configured sidecar address. For Docker, follow the shared-network placement rather than assuming the application's localhost reaches another container. |
| Local health reports `bundleValid: false`. | The process has no usable signed configuration or the loaded one has expired. | Read its synchronisation error and deployment status; check API reachability and deployment credentials. Wait for valid configuration before relying on Enforce. |
| The function returned in Observe, but no Action is visible yet. | Observe can complete while a report is queued or its check is unavailable. | Inspect the SDK's observation result, `recordingStatus`, local health and reporting queue. Search the exact Action key in the correct deployment. |
| `pendingReports` stays above zero. | Durable reports are waiting for delivery. | Inspect network/authentication and synchronisation errors, then watch delivery after correcting them. Preserve the queue; delivery alone does not resume an approval. |
| `blockedReports` is above zero. | A saved decision report is blocked from delivery, for example because its application key no longer accepts reports. | Keep the queue and the related key, Action and attempt references. Review the reported recording gap and key-rotation history; do not delete it or rerun the operation to manufacture a replacement report. |
| The request has an allowed decision but no confirmed effect. | Permission was granted; the application may still be waiting, may have failed, or may have lost a response. | Read execution reports and the application's task. If an effect is uncertain, reconcile the original provider request as described in [recovery](/docs/recovery). |
| A reviewer approved, but the application is still waiting. | Review is complete but the application has not resumed the saved continuation. | Check the originating application's task/worker and approval expiry. Do not submit a second operation to make it continue. |
| Actions arrive, but the Collector shows no trace or metric. | Optional telemetry configuration or export failed separately from Action reporting. | Check the operated process's OTLP setting, Collector base URL and receiving service. Guided setup does not forward the OTLP setting to its child process. |

For support, keep the component version, time, request/Action/attempt references
and a redacted diagnostic message. Do not include tokens, private keys, raw
arguments or provider responses in a public report. A customer-visible Runtime
log, an Action's retained history and a provider's own record answer different
questions; use each for the part of the problem it can establish.

## Send optional monitoring data to your own service

The sidecar can export **traces**, which follow a request's technical steps,
and **metrics**, which count or measure repeated activity. It sends them through
**OpenTelemetry Protocol (OTLP)** to your team's **Collector**, a process that
forwards the data to your monitoring service. Action reports still reach
AuthRail through their separate reporting connection.

Ask your operations team for its OTLP/HTTP Collector base URL, then set
`AUTHRAIL_OTLP_ENDPOINT` in the sidecar's process configuration. For a native
process with its other connection settings already supplied:

```sh
export AUTHRAIL_OTLP_ENDPOINT="https://collector.example.com:4318"
./authrail-sidecar
```

The sidecar adds `/v1/traces` and `/v1/metrics`. For a Docker process managed by
your own deployment tooling, supply the same value in its container environment.
Use your Collector's address here, not the AuthRail API URL, and check the
receiving service for traces and metrics.

Guided setup does not forward this telemetry setting to its native child
process or offer an OTLP flag. Use the [manual process configuration](/docs/configuration)
when enabling export. Leaving the setting unset disables it. The exporter does
not send process log lines. An unavailable monitoring service does not stop an
Action; investigate failed Action delivery separately.

<details className="guide-details">
<summary>Investigate slowness or prepare for maintenance</summary>

A request may include data lookups, contextual assessment, the local rule check,
required reports, the provider function and a result check. Measure these parts
separately when investigating response time, with the selected Rails and
installation settings recorded alongside typical and slow runs. Human review
is a separate waiting period.

Trace identifiers help correlate those technical events, without granting
permission. Keep credentials, prompts, documents and provider bodies out of
diagnostic fields. `telemetryFailures` counts dropped telemetry and export
errors; it does not confirm that the Collector retained an event.

Before restarting or upgrading, pause work and preserve the whole private state
directory, including keys, credentials, queued reports and recovery history.
Check the new process's rules and queues before resuming. Restoring an older
snapshot to remove a warning can also remove recovery information, so follow
the [compatibility and upgrade guidance](/docs/compatibility).

</details>
