A **Rail** is a rule AuthRail checks for an action your application can perform.
For example, a payment rule may allow small payments and require a person's
approval above a limit. Another rule may keep a code-review comment internal.

Use Rails when an organisational expectation needs to be checked at the actual
application call or result. The application adapter applies the decision at the
protected function; publishing a document alone does not add that check.

## Add a payment-review rule

For this example, suppose a published Policy requires approval for payments
above the organisation's automatic limit. The payment action must already be
reviewed in AuthRail. Its saved description, called an **Operation**, defines
the information the application supplies and the result it returns.

### 1. Open the action's rule setup

Open **Rails** and choose **Create Rail**. Select the kind of Rail and the
reviewed payment action. Read its amount, account and target fields before
writing the condition.

| Kind | What it supplies |
| --- | --- |
| Guard Rail | A boundary on input, results or information flow, with supported processing where needed. |
| Data Rail | A reviewed source of business context, such as an invoice balance or a model's answer about a message. |
| Policy Rail | A rule drawn from a published organisational Policy. |

Choose a **Policy Rail** for this payment expectation and select the published
Policy version that supplies it.

<ProductShot src="/screenshots/rails-catalogue.jpg" alt="Rails catalogue listing Guard, Data and Policy Rails" caption="The catalogue keeps different rule types together. An application's deployment selects the published Rails it will use." />

### 2. Describe the condition and outcome

Set the payment condition and the required outcome. For example, an amount
above the reviewed limit requires human approval. Keep the allowed account and
invoice boundaries clear so approval of an amount does not grant access to
another record.

If the decision needs information not supplied by the requested arguments,
choose the reviewed fact source. [Facts and contextual AI](/docs/facts) explains
how the application supplies that information.

### 3. Try examples before publication

Add a normal allowed request, a request outside the boundary and a request that
needs approval. Include a missing-context case if the rule uses facts. Run Rail
validation and read the outcome and reasons for each example.

Validation checks the rule against the examples. It does not pay an invoice or
send a message. Revise the draft if it does not express the intended expectation.

### 4. Publish and select the rule

Publish the reviewed Rail, then select that version for the application's
deployment. A deployment is the configured installation of an application with
its own identity and selected rules.

The expected result is a tested, published rule selected for the intended
application. Confirm its behaviour through real safe application requests in
[Observe](/docs/modes) before relying on Enforce protection.

## Example: register processing for one text field

A Guard can require a trusted function to process a string before the call or
result check. For example, a demo application may remove the literal marker
`DEMO_SECRET` from a draft comment. This example removes **only that marker**;
it is not a general detector or remover of sensitive information.

In the Guard editor, open **Developer configuration · required processing**
and select **Reviewed string field**, such as `arguments.message`. Use **Registered handler ID** `remove_demo_marker`, **Processing**
`sanitize`, and its version to the reviewed implementation's 64-character
lowercase SHA-256 fingerprint. The developer registers the same ID, kind and
fingerprint in the protected application. If the code changes, review its new
fingerprint and update the Guard before using it.

Here `config` is the private sidecar connection configuration from your SDK
guide, including its signing key. `reviewedHandlerSha256` is the fingerprint
you reviewed for this code, not a hash of a user's message. `operation` is the
reviewed comment action with application-authenticated identity and a stable
business key. `saveComment` is your existing protected application function;
it must use the **checked** arguments the SDK gives it and the execution's
provider idempotency key when recording its effect.

<Tabs items={['Node.js', 'Go', 'Python']} groupId="sdk-language" persist>
<Tab value="Node.js">

```ts
import { EnforceClient, type GuardHandler } from '@authrail/sdk-node';

const removeDemoMarker: GuardHandler = {
  id: 'remove_demo_marker', version: reviewedHandlerSha256, kind: 'sanitize',
  process(value) {
    if (Buffer.byteLength(value, 'utf8') > 4096) {
      throw new Error('Comment is too large for this handler');
    }
    return value.replaceAll('DEMO_SECRET', '[removed]');
  },
};
const client = new EnforceClient({ ...config, guardHandlers: [removeDemoMarker] });
const checked = await client.enforce(
  operation, { message: 'Please remove DEMO_SECRET from this demo.' },
  (checkedArguments, execution) => {
    if (typeof checkedArguments.message !== 'string') {
      throw new Error('Expected a checked comment string');
    }
    return saveComment(checkedArguments.message, {
      idempotencyKey: execution.providerIdempotencyKey,
    });
  },
);
```

// Imports: context, errors, strings, and
// authrail "github.com/AuthRail/authrail-sdk-go".
config.GuardHandlers = []authrail.GuardHandler{{
    ID: "remove_demo_marker", Version: reviewedHandlerSHA256, Kind: "sanitize",
    Process: func(ctx context.Context, value string) (string, error) {
        if err := ctx.Err(); err != nil { return "", err }
        if len(value) > 4096 { return "", errors.New("comment is too large") }
        return strings.ReplaceAll(value, "DEMO_SECRET", "[removed]"), nil
    },
}}
client, err := authrail.NewClient(config)
if err != nil { return err }
type CommentArguments struct { Message string `json:"message"` }
_, _, _, err = authrail.Enforce(ctx, client, operation,
    CommentArguments{Message: "Please remove DEMO_SECRET from this demo."},
    func(callCtx context.Context, checked CommentArguments, execution authrail.ExecutionContext) (map[string]any, error) {
        return saveComment(callCtx, checked.Message, execution.ProviderIdempotencyKey)
    })
if err != nil { return err }
```

from authrail import AsyncEnforceClient, ExecutionContext, GuardHandler, JSONObject


def remove_demo_marker(value: str) -> str:
    if len(value.encode("utf-8")) > 4096:
        raise ValueError("Comment is too large for this handler")
    return value.replace("DEMO_SECRET", "[removed]")


handler = GuardHandler(
    id="remove_demo_marker", version=reviewed_handler_sha256,
    kind="sanitize", process=remove_demo_marker,
)

async def save_checked_comment(
    checked_arguments: JSONObject, execution: ExecutionContext,
) -> JSONObject:
    message = checked_arguments["message"]
    if not isinstance(message, str):
        raise ValueError("Expected a checked comment string")
    return await save_comment(
        message,
        idempotency_key=execution.provider_idempotency_key,
    )

async with AsyncEnforceClient(**config, guard_handlers=[handler]) as client:
    checked = await client.enforce(
        operation, {"message": "Please remove DEMO_SECRET from this demo."},
        save_checked_comment,
    )
```

When the published Guard requires this handler for `arguments.message`, the SDK
processes that string before its final call check. If the call is permitted,
`saveComment` receives the processed value, such as
`Please remove [removed] from this demo.` A rule targeting `result.message`
instead processes that returned field before checking what may reach the agent.
Do not call the processor manually and assume that fulfills a Guard: the
adapter obtains the reviewed processing plan and records its signed evidence.

The handler only changes its selected string; it must not post a comment or
perform another business effect. The SDK checks required processing and the
resulting values. A missing or failed handler stops Enforce. Observe does not
run these handlers, and processing does not override a denial or missing
approval.

<details className="guide-details">
<summary>More about versions and later changes</summary>

A draft can change; a published Rail Version cannot be edited. Older Actions
keep the rule version used for their decision even after you publish an
improvement.

A new publication does not silently replace a deployment's selection. Review
and update that selection deliberately. If a decision is unexpected, inspect
the selected version and the version saved on the Action before editing a draft.

Examples and historical replay are Rail-validation tools, separate from the
two Runtime deployment modes, Observe and Enforce.

</details>

<details className="guide-details">
<summary>More about processing and trusted facts</summary>

Some Guard rules require `sanitize` for content cleanup, `transform` for a value
change or `isolate` for a supported containment step. The application registers
the trusted code for that step, called a **handler**. The rule identifies its
version and the field it must process; the adapter invokes only a matching
handler and signs evidence of the processed value before the final decision.

Missing handlers, conflicting targets and unsupported isolation stop Enforce.
Processing does not override a denial or approval requirement. Observe remains
advisory and does not transform the real input or result.

Handlers must not perform business effects such as posting a comment or moving
money. A signed handler report does not independently establish the quality of
redaction or isolation. See [NVIDIA OpenShell](/docs/openshell) for its supported
containment path.

The protected application performs reviewed fact lookups; the sidecar checks
the signed answers. An imported schema does not create a provider connection
or make a source trustworthy. A failed lookup is not a zero balance or a
negative sensitivity answer. Configure and test the rule's unavailable behaviour.

</details>
