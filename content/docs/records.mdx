An **Action** brings together the history of one Runtime request: the application
and AI system, rule checks, approval and execution reports. It is the place to
look when someone asks why a payment was stopped or whether an allowed account
change was completed.

These are different questions. A decision establishes permission, while an
execution report records what the application said happened. To establish an
external effect independently, you also need the matching provider record or
another authoritative source. Keeping those distinctions helps you explain an
outcome without promising more than the available records show.

## Follow a request in AuthRail

### 1. Find its Action

Open <a href={AUTHRAIL.clientOrigin}>AuthRail</a> and choose **Actions & decisions**, or follow **View in AuthRail** from the originating
application. Check the AI system, deployment, target and mode so you are reading
the intended request. In Observe, a completed operation can appear beside a
**Would deny** check because Observe did not stop it.

### 2. Read why it was allowed or stopped

Begin with **Permission to run** and **Why this decision was made**. **Before
running** explains the call check, and **Before returning the result** explains
what could reach the agent afterward. The page uses the explanation saved with
the decision, where available.

**Information used for the decision** shows the status and age of its source
readings. **Rails used for this request** opens the versions used at that time,
even when the deployment now selects different ones. If a person reviewed the
request, follow its approval to see the reviewers, deadline and decision.

### 3. Look at the application's report

Expand **What the application reported** to follow the attempt's start,
completion, failure or uncertainty. Compare it with the result check: a function
can finish while its returned information is withheld from the agent.

| Outcome shown | How to read it |
| --- | --- |
| Outcome not reported | No execution outcome was saved for this attempt. |
| Permission granted | The call received permission; no execution outcome has been reported. |
| Awaiting approval | A person's decision is needed before the saved request can continue. |
| In progress | The application reported starting the attempt. |
| Completed | The authenticated executor reported completion. |
| Failed | The authenticated executor reported failure. |
| Outcome unknown | The effect needs investigation before another attempt. |

**Completed** describes the executor's report, not a provider lookup performed
by AuthRail. If you need to confirm a provider change, match its account and
reference with the provider's record. [Recovery](/docs/recovery) explains what
to do when the effect cannot yet be established. A list's **Latest check** may
be the later result check, so use **Permission to run** for the original call.

### 4. Follow the related activity

An **Activity Record** places a meaningful event in its organisational context,
while the Action keeps the Runtime checks and attempt reports together. On the
linked Activity Record, begin with **Recorded outcome** and its timeline.
**Saved record details** and **Technical references** provide supporting data,
and **Original recorded wording** makes a translated historical summary available.
Descriptions written by people keep their original wording.

## Keep the reference with your application's task

Saving the Action ID with a payment or workflow task makes it easier for an
operator to find the same request later. The SDK returns its decisions alongside
the check result. These helpers show the useful metadata without printing the
business input, result or private continuation. Keep identifiers in private
diagnostic fields rather than metric labels.

<Tabs items={['Node.js', 'Go', 'Python']} groupId="sdk-language" persist>

<Tab value="Node.js">

```ts
import type { ObserveDecision } from '@authrail/sdk-node';

function logDecision(decision: ObserveDecision | null | undefined) {
  if (!decision) return;
  console.log(JSON.stringify({
    actionId: decision.actionId,
    certificateId: decision.certificateId,
    outcome: decision.outcome,
    recordingStatus: decision.recordingStatus,
  }));
}
```

After Enforce, pass `checked.callDecision` and `checked.resultDecision` to this
helper. In Observe, await the run's `observation`, then pass
`checks.callDecision` and `checks.resultDecision`; inspect the separate errors
if a decision is absent.

</Tab>

<Tab value="Go">

```go
import (
    "log"
    authrail "github.com/AuthRail/authrail-sdk-go"
)

func logDecision(decision *authrail.Decision) {
    if decision == nil { return }
    log.Printf("actionId=%s certificateId=%s outcome=%s recordingStatus=%s",
        decision.ActionID, decision.CertificateID,
        decision.Outcome, decision.RecordingStatus)
}
```

Pass the call and result decisions returned by `authrail.Enforce`. In Observe,
receive the observation channel first and use `CallDecision` and `ResultDecision`,
checking the accompanying error when a decision is absent.

</Tab>

<Tab value="Python">

```python
import json
from authrail import Decision


def log_decision(decision: Decision | None) -> None:
    if decision is None:
        return
    metadata = decision.as_dict()
    print(json.dumps({
        "actionId": decision.action_id,
        "certificateId": metadata.get("certificateId"),
        "outcome": decision.outcome,
        "recordingStatus": decision.recording_status,
    }))
```

After Enforce, pass `checked.call_decision` and `checked.result_decision`.
In Observe, await `run.observation` and use the same fields, with `call_error`
and `result_error` explaining any check that did not finish.

</Tab>

The recording status tells you where that report is. `retained` means AuthRail
has acknowledged it; `queued` means the sidecar is still waiting to deliver it.
Display that distinction in the application so a locally queued report is not
presented as already saved in the workspace. The [SDK guides](/docs/getting-started)
show where the decisions fit around a function call.

<details className="guide-details">
<summary>Certificates, execution reports and downloads</summary>

A **Decision Certificate** is the signed account of a check, its rule versions
and reasons. An **execution receipt** is the executor's signed report about an
attempt. Approval records describe a person's review and the permission to
continue. Runtime logs serve a different purpose again: diagnosing the
installation rather than replacing these business records.

Open **Decision certificates** and choose **Download signed certificate** to
keep the statement and signature. The page displays its claim; it does not
independently verify the signature in your browser. **Download execution report**
also includes the executor statement, signature and public-key snapshot where
available. Older reports without that material remain labelled as such.

Signature verification can detect a changed statement and identify its key.
It cannot establish that a provider completed the operation or that every
possible route was intercepted. For example, a saved denial does not rule out
a separate direct provider call. Compare the application's or provider's history
when a reported start or effect needs investigation.

</details>

<details className="guide-details">
<summary>Caller identity and model information</summary>

**About this request** contains the AI system, deployment, time and caller
context saved with the request. **Model configuration**, **Application
verification** and **Technical references** provide additional diagnostic detail.
Later inventory edits leave this historical context unchanged.

Configured provider and model names describe the setup; they do not establish
which model generated a particular request. Similarly, a contextual assessment's
identity, status and signed finding explain the information used by a rule,
without including its source text or proving the original agent's model identity.
Unreported execution identity remains unreported.

Organisation permissions govern access to these records. An internal support
role does not automatically expose tenant content.

</details>

<details className="guide-details">
<summary>Use Runtime records in compliance work</summary>

The Action's certificates, reports and Rail Versions describe the historical
request. A later rule cannot replace those versions, and an older record does
not acquire a missing signature merely because newer records include one.

To use this history as compliance proof, a Control's Test or Evidence requirement
sets the period, coverage, completeness, freshness and review it needs. See
[Framework proof](/docs/framework-proof). Record integrity and an application's
reported effect remain distinct from independent effect verification and from
legal certification.

</details>
