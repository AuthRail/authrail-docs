A payment request can time out after the provider has made the payment but
before your application receives the response. An immediate retry could pay
twice. Recovery starts with the original request: find its saved attempt, check
the provider or business ledger, and report what that source establishes.

AuthRail keeps the permission decision and the application's execution reports
separately. An allowed decision explains why the request could proceed; it
cannot tell you what happened after a lost response. Use this guide when an
application crashes, reporting is interrupted or an Action shows **Outcome
unknown**.

## Investigate the original attempt

The application's developer or operator can follow the request without repeating
its business operation:

1. Pause automatic retries for this task and keep its original arguments,
   Action and attempt IDs, and provider request key.
2. Open the Action and read **Permission to run** and **What the application
   reported**. An attempt with a start report may have reached the provider.
3. Look up the original operation in the same provider account or your durable
   business ledger. Match its request key, resource and amount or other details
   that identify the intended effect.
4. Report the established outcome through the SDK. Report success when the
   source confirms the effect, and failure only when it confirms no effect.
   If it cannot establish either answer, keep the task unknown for investigation.

This process is called **reconciliation**. It updates the original attempt
rather than performing the payment again. A timeout, HTTP error or recollection
from a chat does not establish that no payment happened.

## Save recovery information before calling the provider

The SDK gives the Enforce callback an execution context identifying its attempt
and provider idempotency key. Save that context with the business request before
calling the provider, so another process can investigate it after a crash.
A provider **idempotency key** lets a supporting provider recognise a repeat
of the same intended request; check the provider's own behaviour before relying
on it to prevent duplicates.

These examples continue the [SDK setup](/docs/getting-started). `client`,
`operation` and `payment` belong to your application, with the original version,
authenticated identities and business request key. `recoveryStore` or
`recovery_store` encrypts the context and binds it to the organisation, user,
deployment and task in `binding`. Its load function checks that same binding,
and the reconciliation worker claims the task exclusively.

The `provider` methods are also application code. `pay` performs the operation
using the supplied idempotency key. `lookupOriginal` queries the same account
for that original request and returns a validated state of `succeeded`, `failed`
or `unknown`, plus a provider reference. In this example, `failed` specifically
means the lookup confirmed no effect, not that the lookup itself failed.

<Tab value="Node.js">

```ts
import { EnforceOutcomeUnknownError, type ExecutionContext } from '@authrail/sdk-node';

async function executePayment() {
  try {
    return await client.enforce(operation, payment, async (checked, execution) => {
      await recoveryStore.saveEncrypted(binding, JSON.stringify(execution));
      return provider.pay(checked, execution.providerIdempotencyKey);
    });
  } catch (error) {
    if (error instanceof EnforceOutcomeUnknownError && error.recovery) {
      try {
        await recoveryStore.saveEncrypted(binding, JSON.stringify(error.recovery));
      } catch {
        console.error('Recovery storage unavailable; keep this task unresolved');
      }
    }
    throw error; // Keep the task unresolved; do not pay again here.
  }
}

async function reconcilePayment() {
  const recovery: ExecutionContext = JSON.parse(await recoveryStore.loadEncrypted(binding));
  const found = await provider.lookupOriginal(recovery.providerIdempotencyKey);
  if (found.state === 'unknown') return; // Leave the saved task for investigation.
  await client.reconcile({ ...recovery,
    providerReference: found.reference, outcome: found.state });
}
```

```go
// Imports: context, encoding/json, errors, and authrail "github.com/AuthRail/authrail-sdk-go".

func executePayment(ctx context.Context) error {
    _, _, _, err := authrail.Enforce(ctx, client, operation, payment,
        func(ctx context.Context, checked map[string]any, execution authrail.ExecutionContext) (map[string]any, error) {
            encoded, err := json.Marshal(execution)
            if err != nil { return nil, err }
            if err := recoveryStore.SaveEncrypted(ctx, binding, encoded); err != nil { return nil, err }
            return provider.Pay(ctx, checked, execution.ProviderIdempotencyKey)
        })
    var unknown *authrail.OutcomeUnknownError
    if errors.As(err, &unknown) {
        encoded, saveErr := json.Marshal(unknown.Recovery)
        if saveErr != nil { return errors.Join(err, saveErr) }
        if saveErr := recoveryStore.SaveEncrypted(ctx, binding, encoded); saveErr != nil {
            return errors.Join(err, saveErr)
        }
    }
    return err // Keep an unknown task unresolved; do not pay again here.
}

func reconcilePayment(ctx context.Context) error {
    encoded, err := recoveryStore.LoadEncrypted(ctx, binding)
    if err != nil { return err }
    var recovery authrail.Recovery
    if err := json.Unmarshal(encoded, &recovery); err != nil { return err }
    found, err := provider.LookupOriginal(ctx, recovery.ProviderIdempotencyKey)
    if err != nil { return err }
    if found.State == "unknown" { return nil } // Keep the saved task unresolved.
    _, err = client.Reconcile(ctx, recovery, found.Reference, found.State)
    return err
}
```

<Tab value="Python">

```python
import json
from authrail import EnforceOutcomeUnknownError, ExecutionContext

async def execute_payment():
    async def pay(checked, execution):
        await recovery_store.save_encrypted(binding, json.dumps(execution.as_dict()))
        return await provider.pay(checked, execution.provider_idempotency_key)

    try:
        return await client.enforce(operation, payment, pay)
    except EnforceOutcomeUnknownError as unknown:
        try:
            await recovery_store.save_encrypted(binding, json.dumps(unknown.recovery.as_dict()))
        except Exception as storage_error:
            raise unknown from storage_error
        raise  # Keep the task unresolved; do not pay again here.


async def reconcile_payment():
    saved = await recovery_store.load_encrypted(binding)
    recovery = ExecutionContext.from_dict(json.loads(saved))
    found = await provider.lookup_original(recovery.provider_idempotency_key)
    if found.state == "unknown":
        return  # Keep the saved task for investigation.
    await client.reconcile(recovery, found.state, found.reference)
```

The SDK's reconciliation response belongs to the original attempt. Use it to
update the task, leaving an unknown lookup unresolved even when the worker
returns normally. If recovery storage fails, keep the task held for investigation
as well; losing its journal does not establish failure or make a retry safe.
The signed report records what the executor established through its lookup,
rather than an independent provider lookup performed by AuthRail.

## Decide what can happen next

When the provider confirms completion, show the existing effect and its
reference instead of executing again. When it confirms no effect, the
application can seek a fresh decision and, where required, fresh facts and
approval for another attempt. An unresolved lookup stays with an operator.

For another attempt at the same intent, keep the original arguments, provider
request key and AuthRail Action key. The Action key is the application's stable
identity for this business request; replacing it would create a different
request without resolving the first one. Reusing it with changed arguments is
also not a way to update that earlier request.

A person may explicitly ask for different work, such as another amount or target.
That is a new intent needing its own decision, so a prior denial does not impose
a blanket ban on later requests. The application still needs to distinguish
that new instruction from splitting work to evade a rule or repeating a write
whose effect remains unknown.

## When a result was withheld

An invoice may be created successfully before a result check stops its sensitive
fields from reaching the agent. Withholding the response does not delete the
invoice. Inspect the execution reports and provider record before treating an
SDK error as a failed write. If the operation needs reversal, use the business
application's supported reversal process.

## Restore reporting without repeating the operation

A sidecar can have reports waiting locally even while some of the Action is
visible in AuthRail. Check the recording status to see which part needs repair:

| Status | Meaning | Next step |
| --- | --- | --- |
| `retained` | AuthRail acknowledged the report. | Keep its reference with the application task. |
| `queued` | The sidecar saved the report locally for delivery. | Restore connectivity and preserve its state directory. |
| `unavailable` | The report could not be durably recorded. | Investigate storage and delivery using the application's recovery information. |

Enforce waits for the required call report before a new operation runs. Delivering
that report later does not automatically start the waiting function, while a
reporting failure after execution cannot reverse its effect. Observe remains
advisory during the same outage.

Keep the whole sidecar state directory across restarts, including queues,
session history and recording-gap files. They are part of the information
needed for recovery. [Diagnostics](/docs/operations) shows how to check the
connection and local process without clearing those records.

<details className="guide-details">
<summary>What to keep in the execution journal</summary>

Before Enforce invokes the business function, the adapter sends a signed
`started` report to AuthRail. Your application's journal then preserves the
callback's recovery context alongside the original business input: the Action
ID, attempt ID, provider idempotency key and any approval permit reference.
The provider key has the form `ar-<Action ID>`; save the value the SDK supplies
rather than reconstructing an attempt after a crash.

Node's `reconcile`, Go's `Reconcile` and Python's `reconcile` take that context,
a known outcome and provider reference. Their reports use
`reconciled_succeeded` or `reconciled_failed` and do not invoke the business
function again.

</details>

<details className="guide-details">
<summary>Renew an expired Enforce selection</summary>

An expired signed selection cannot grant permission. In **AI Inventory**, open
the deployment's **Overview → Selected Rails** and use **Renew current Rails**
where available. Check the versions and confirm that the function and credential
arrangements still apply, then wait for a valid configuration and current
connection health before continuing work.

On a compatible server, a sidecar's authenticated connection update can renew
an unchanged Enforce selection near or after expiry. The server rechecks the
selected versions, credential, AI system revision and the authority behind the
last confirmation. If those checks fail, the selection stays blocked; consult
[compatibility](/docs/compatibility) for your installed components.

Renewal keeps the current rules and mode. It does not publish drafts, select
newer versions, restore a revoked deployment, extend an approval or repeat a
business operation. Once configuration is restored, a saved request still
continues through its own approval or recovery flow.

</details>

<details className="guide-details">
<summary>Reports rejected after an application-key change</summary>

A decision report signed by an old key may become a blocked recording gap once
that key's acceptance window closes. A local operator can inspect its safe
metadata and acknowledge the gap with a reason. This records the delivery gap
locally; it cannot manufacture a central Action or Decision Certificate or
claim that the request was enforced.

An execution outcome may also remain queued after its decision becomes visible.
Acknowledging a decision gap does not resolve a rejected execution report.
Keep the original business ledger and sidecar state while investigating both
delivery and the provider effect.

</details>
